# 0002 — JSON Schema Draft 2020-12 as the canonical machine-verifiable structure

## Status

Accepted — 2026-07-30. Applies to specification version 0.1.

## Context

A specification that cannot be validated is implemented differently by everyone who reads it. The
project therefore needs a machine-verifiable definition of the event structure, in a format that:

- Has mature, maintained validators in many languages.
- Can express conditional rules, not just field presence and types.
- Can reject unknown properties.
- Can be resolved and validated entirely offline.
- Is a published standard rather than a project invention.

Candidates were JSON Schema (several drafts), Protocol Buffers, Avro, CUE, TypeSpec, and prose plus
per-language type definitions.

The rules the model needs to express include several that are conditional: a failure carries an error;
acting for a principal identifies that principal; a digest requires its algorithm. These are the rules
most likely to be implemented inconsistently if they exist only as prose.

## Decision

**JSON Schema Draft 2020-12** defines the canonical machine-verifiable structure of an OpenAuditModel
event.

The canonical schema is identified by `https://openauditmodel.org/schemas/audit-event/0.1/schema.json` and lives at
[schemas/v0.1/audit-event.schema.json](../schemas/v0.1/audit-event.schema.json).

Constraints on how the schema is written:

1. Every rule expressible in Draft 2020-12 is expressed there rather than only in prose.
2. Core objects set `additionalProperties: false`.
3. Conditional rules use `if`/`then` and `dependentRequired`.
4. Recursive free-form values are defined once in `$defs` and referenced.
5. Regular expression patterns use no look-around and no back-references, so that behaviour is
   identical across ECMA-262, RE2 and PCRE engines. This is enforced by a test.
6. No `$ref` resolves to a remote location. Validation never requires a network call.
7. Where a rule cannot be expressed — "do not record secrets" — the specification states that
   explicitly rather than implying validation covers it.

## Consequences

**Positive**

- Validators exist and are maintained in JavaScript, Python, Go, Java, .NET, Rust and others, so
  conformance can be checked in any implementation language.
- Conditional rules are enforced rather than merely documented.
- `additionalProperties: false` turns "I added a field nobody reads" into a validation error.
- 2020-12 fixes real problems in earlier drafts: `$defs` and `$ref` with siblings, `prefixItems`,
  `dependentRequired`, and clearer annotation semantics.
- The schema doubles as machine-readable documentation, since every property carries a description.

**Negative**

- Draft 2020-12 support is less universal than Draft 7. Some ecosystems still default to Draft 7, and
  adopters may need a newer validator.
- Error messages from schema validators are poor by default. This is why the conformance CLI
  translates them into JSON Pointer paths and readable messages rather than printing them raw.
- JSON Schema cannot express everything that matters. Semantic rules — a `subject` misused as a
  target, an event name whose meaning changed — remain prose and remain unenforceable by tooling.
- `additionalProperties: false` composes awkwardly with `allOf`, which constrains how the schema can
  be factored.

**Neutral**

- JSON is assumed as the interchange representation. Other encodings can carry the same model, but
  the canonical definition is JSON-shaped.

## Alternatives considered

**JSON Schema Draft 7.** Rejected: wider support, but no `dependentRequired`, awkward `$ref` sibling
handling, and adopting a superseded draft for a new specification guarantees a migration later.

**Protocol Buffers or Avro.** Rejected: excellent for wire compatibility, poor for expressing
conditional validation rules, and both push the model toward a specific serialization and toolchain.
Neither can express "when outcome is failure, error is required".

**CUE or TypeSpec.** Rejected: more expressive than JSON Schema, with far fewer validators in the
languages adopters actually use. A specification whose conformance can only be checked with one
toolchain is not language-neutral.

**Prose plus per-language types.** Rejected: this is the current situation everywhere, and it is what
the project exists to replace.
